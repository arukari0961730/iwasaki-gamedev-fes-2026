## これからやりたいこと

### Q. このサイトで、これから改善したいことはありますか？

**答えの例**
> すぐにできそうなものが2つあります。1つ目は、ゲーム一覧から各ゲームの詳しい紹介ページを開けるようにすることです。ゲームの情報は games.json にまとめているので、説明の項目を足して、ランキングページと同じようにゲームの ID で表示を切り替える1つのページを作れば対応できます。2つ目はプレイ映像を載せることで、動画は重く会場の電波や無料枠の転送量に影響するので、動画サービスに置いて埋め込む形を考えています。長期的には、ページから直接ゲームを起動できるようにしたいです。ブラウザは安全のために PC の中のプログラムを直接動かせないので、Unity の WebGL のように、ブラウザで動く形に書き出して公開する方法を検討しています。

**深掘りされたら**
- **なぜブラウザから PC のゲームを起動できないのか**：Web サイトが PC の中のプログラムを勝手に動かせると、悪意のあるサイトを開いただけでウイルスを実行されてしまう。そのため、どのブラウザでも禁止されている
- **動画をサイトに直接置かない理由**：Firebase Hosting の無料枠は1日の転送量に上限があり、動画は画像よりずっと大きい。動画サービスなら、画質の自動調整もしてくれる

## テーマ6：キャッシュ（開発中に難しかったこと）

### Q. 開発中に難しかったことや、困ったことはありますか？

**答えの例**
> ゲームを追加してサイトを更新したとき、ある PC だけトップページのほとんどが表示されなくなったことがありました。他の端末では更新後のページが正しく表示されていたので、その PC に原因があると考えて調べたところ、ブラウザのキャッシュが原因でした。Firebase Hosting は初期設定で、ファイルをブラウザに1時間保存させるようになっていて、その PC は新しい HTML と、保存してあった古い JavaScript を組み合わせて使っていました。新しい HTML が古い JavaScript にない機能を呼んでエラーになり、画面を組み立てる処理が止まっていたんです。そこで、HTML や JavaScript は使う前に毎回サーバーに新しいかを確認する設定にし、画像だけは通信量を抑えるために保存させる、というようにファイルの種類ごとに設定を分けました。文化祭の当日に更新しても同じことが起きないように、本番前に気づいて直せたのはよかったです。この経験から、「ファイル同士の新しさが食い違うと壊れる」ことと、更新したら別の端末だけでなく、前に開いたことのある端末でも確認する大切さを学びました。

**話す順番**：症状 → 切り分け（他の端末では正常）→ 原因 → 対策 → 学んだこと

**押さえるキーワード**
- キャッシュ：一度もらったファイルをブラウザに保存して使い回すこと
- Cache-Control：サーバーが「何秒保存していいか」を指示する見出し。Firebase の初期設定は1時間（`max-age=3600`）
- **原因の核心**：新しい HTML と古い JS の**食い違い**
- 対策：HTML・JS・CSS・JSON は `no-cache`（保存はするが毎回確認）、画像は1時間保存

### Q. `no-cache` にすると遅くなりませんか？

**答えの例**
> `no-cache` は「保存しない」ではなく、「保存はするけど、使う前に毎回新しいか確認する」という意味です。変わっていなければ、サーバーは中身を送り直さずに「そのまま使っていい」という短い返事（304）を返すので、ほとんど遅くなりません。通信量が一番多い画像は、これまでどおり保存させています。

### Q. ほかの解決方法はありますか？

**答えの例**
> ファイル名に版の番号を入れる方法があります。中身が変わるたびに `games.a1b2c3.js` のように名前を変えれば、ブラウザは別のファイルとして必ず新しいものを取りに行くので、長く保存させても食い違いが起きません。大きなサイトではこちらが一般的ですが、普通はビルドの道具で自動的に名前をつけます。今回はビルドの工程なしで作っていたので、設定1つで直せる方法を選びました。

## テーマ5：API

### Q. API とは何ですか？ このサイトではどこで使っていますか？

**答えの例（短く）**
> API は、外部のプログラムやサービスに処理をお願いするための、決められた窓口と頼み方のことです。このサイトでは、データベースの Firestore の API を、Firebase が用意している SDK を通して使っています。たとえば、ランキングを読み込むときやスコアを登録するときは、SDK の関数を呼ぶと、裏で Firestore にリクエストが送られて結果が返ってきます。

**答えの例（少し詳しく）**
> ランキングの表示では、SDK の `onSnapshot` を使って「データが変わったら教えて」と Firestore に頼んでいて、スコアの登録では `runTransaction` で「読んで、比べて、良ければ書く」を1つの処理として頼んでいます。ほかにも、ゲーム情報の読み込みには、ブラウザの API の `fetch` を使っています。

**押さえるキーワード**
- API ＝ 別のプログラムに仕事を頼む「決められた窓口と頼み方」（レストランのメニューと注文票）
- **Firestore の API** を **SDK 経由**で使っている（SDK ＝ API を関数として呼べるように包んだ道具）
- 具体例：`onSnapshot`（ランキングの見張り）、`runTransaction`（登録）、`fetch`（games.json の読み込み）

### Q. API と SDK の違いは何ですか？

**答えの例**
> API は、相手のサービスが決めた「頼み方のルール」で、SDK は、そのルールどおりに頼んでくれる道具です。Firestore の API を直接使うと、URL やデータの形を自分で組み立てる必要がありますが、Firebase の SDK を使うと `getDoc` のような関数を呼ぶだけで済みます。リアルタイム更新やトランザクションのように、自分で作ると大変な仕組みも SDK が用意してくれています。

**覚え方**：API ＝ 注文の受け方のルール（窓口）、SDK ＝ 注文アプリ（道具）

### Q. Firebase の API キーがコードに書いてありますが、大丈夫なんですか？

**答えの例**
> 大丈夫です。Firebase の API キーは「どのプロジェクトにつなぐか」を示す名札で、ブラウザに送ることが前提になっています。キーを持っているだけでは、データを読み書きする権限はありません。誰が何をできるかはセキュリティルールで決めていて、たとえば記録の修正は管理者の UID でログインしたときだけです。ただ、Claude API のような「持っている人が使えて、その人に請求が来る」種類のキーは、漏れると悪用されるので、絶対にブラウザ側には置かず、サーバー側（Cloud Functions）だけで使います。

**さらに深掘りされたら**
- キーを使えば誰でも自分のプロジェクトに「頼むこと」はできる（例：新しいアカウントを作る）。でも、ルールは**管理者の UID だけ**を許可しているので、新しく作ったアカウントには何の権限もない
- もっと守りを固めるなら、Google Cloud でキーを使えるサイトを `gamedev-fes-2026.web.app` に限定したり、Firebase の App Check で「本物のサイトからの通信か」を確かめたりできる（今回はやっていない）

## テーマ4：セキュリティルールと認証

### Q. 自分のサーバーがないのに、どうやってデータを守っているんですか？

**答えの例**
> Firestore のセキュリティルールで守っています。このサイトはブラウザから直接 Firestore に読み書きする構成で、接続の情報も公開されているので、画面側のチェックはその気になれば回避できてしまいます。そこで、Google のサーバー側で動くセキュリティルールに「誰が・どんな条件なら書き込めるか」を書きました。たとえば、新しい登録は名前が12文字以内でスコアが整数のときだけ、上書きは前より大きいスコアのときだけ、日時はサーバーの時刻だけを受け付けます。記録の修正や非表示は、Firebase Authentication でログインした管理者の UID のときだけ許可しています。書いたあとに、画面を使わず直接書き込む攻撃を6種類試して、すべて拒否されることを確認しました。

**押さえるキーワード**
- **画面側のチェックは回避できる**（ブラウザで動くので、自分で JavaScript を書けば素通りできる）
- **セキュリティルール**は Google のサーバー側で動くので回避できない ＝ 本当の門番
- **認証（Authentication）**は「誰か」を確かめるだけ。「何をしていいか」を決めて止めているのは**ルール**
- ルールの中で `request.auth.uid` を見て管理者か判定している
- 管理者以外にも、**登録の条件**（形式・文字数・日時・スコアは上がる方向だけ）をルールで守っている
- 実際に攻撃を試して確認した

**よくある間違い**
- 「認証で守っている」だけだと不十分。認証は「誰か」を確かめる仕組みで、守っているのはルール
- 「管理画面を隠している」は守りにならない。ページは誰でも開けるし、直接命令を送れる

### Q. 画面側のチェックは意味がないんですか？

**答えの例**
> 意味はあります。役割が違います。画面側のチェックは、入力ミスをその場で教えるための「使いやすさ」のためで、ルールは本当に守りたいことを守る「安全」のためです。ルールだけだと、入力ミスのたびに「拒否されました」としか出せません。両方を組み合わせています。ただ、NG ワードのチェックは今は画面側だけなので、すり抜けは可能です。文化祭では管理画面で非表示にする運用で補い、今後はサーバー側（Cloud Functions）に移す予定です。

### Q. 管理者はどうやって見分けているんですか？

**答えの例**
> Firebase Authentication のメールとパスワードでログインすると、ユーザーごとの番号（UID）が証明された状態で Firestore に届きます。セキュリティルールでは、その UID が管理者の UID と一致するときだけ、記録の修正や非表示を許可しています。管理画面のページ自体は誰でも開けますが、ルールで止めているので、ログインしていない人はデータを変更できません。

### Q. 文化祭のあと、登録はどうやって締め切ったんですか？

**答えの例**
> ランキングを当日の結果として残すために、登録だけを締め切りました。設定ファイルの値を切り替えて画面から登録ボタンを消し、受付終了の表示にしています。ただ、画面のボタンを消すだけでは直接書き込めてしまうので、セキュリティルールの登録と上書きの条件にも「受付中であること」を足して、サーバー側で確実に拒否するようにしました。直接書き込もうとして拒否されることも確認しています。

### Q. 名前に悪意のある文字列を入れられたらどうなりますか？

**答えの例**
> 名前を画面に表示するときは、HTML として解釈されないように変換（エスケープ）しています。たとえば `<script>` と書かれても、ただの文字として表示されるので、他の人の画面でプログラムを動かされる（XSS）ことはありません。

## テーマ3：データベース

### Q. スコアのデータは、どのように保存していますか？ なぜその形にしたんですか？

**答えの例**
> Firebase の Firestore というデータベースに、`games/ゲームID/scores/プレイヤー名` という形で保存しています。ゲームごとに分けているので、ゲームのランキングを取り出すときはそのゲームの記録だけを見ればよく、ゲームが増えても同じ形で対応できます。プレイヤー名をそのまま記録の ID にしているので、同じ名前で登録すると同じ記録を見に行き、前より良いスコアのときだけ上書きします。これで「同じ人は最高スコアだけ表示する」がデータの形で実現できています。スコアはすべて整数で保存していて、タイムは秒に直しています。数字の大小だけで並べ替えられるので、点数のゲームもタイムのゲームも同じ仕組みで順位を出せます。

**押さえるキーワード**
- **Firestore**（データベース）と **Firebase Hosting**（ファイルの公開）は別のサービス。どちらも Firebase の一部
- コレクション（棚）とドキュメント（カード）
- `games/ゲームID/scores/プレイヤー名`
- 名前を ID にした → 同じ人の記録が1つにまとまる
- 整数で保存（タイムは秒）→ 並べ替えが単純、小数の誤差もない

### Q. なぜ SQL のデータベースではなく Firestore にしたんですか？

**答えの例**
> ランキングは「スコアの大きい順に並べて上から取る」だけで、表をつなげるような複雑な集計がいらなかったからです。一方で、会場のモニターに新しい記録をすぐ反映したかったので、データの変化を自動で知らせてくれるリアルタイム更新が標準で使える Firestore が合っていました。ただ、全ゲームの合計で総合ランキングを作るような集計が必要なら、SQL の方が向いていると思います。

### Q. ランキングはどうやって取り出しているんですか？

**答えの例**
> 「非表示のものを除いて、スコアの大きい順、同点なら記録した時刻の早い順に並べて、上から3件」というクエリで取り出しています。複数の条件を組み合わせているので、Firestore では専用のインデックス（索引）を事前に作る必要があります。公開直後にランキングが表示されなかったのは、このインデックスが作成中だったからでした。

### Q. 会場のモニターは、どうやって自動で更新されているんですか？

**答えの例**
> Firestore の `onSnapshot` という機能を使っています。一度データを取ってくるだけでなく、「このデータが変わったら教えて」と頼んでおく仕組みで、誰かがスコアを登録すると、Firestore から新しいランキングが届いて画面が書き換わります。ページの再読み込みは必要ありません。

### Q. 同じ名前でほぼ同時に登録されたらどうなりますか？

**答えの例**
> 登録の処理は「今の記録を読む → 比べる → 良ければ書く」の3ステップなので、同時に動くと、良い記録が後から来た悪い記録で上書きされるおそれがあります。そこでトランザクションを使って、3ステップをひとまとまりの処理にしています。途中で他の人に書き換えられていた場合は自動でやり直すので、記録が下がることはありません。さらに、セキュリティルールでも「前より大きいスコアのときだけ上書きできる」と制限しています。

## テーマ2：ドメインと URL

### Q. URL を開いてからページが表示されるまでに、裏側で何が起きていますか？

**答えの例**
> まずブラウザが DNS に「`gamedev-fes-2026.web.app` の IP アドレスはどこか」を問い合わせます。返ってきた IP アドレスの Firebase Hosting のサーバーに HTTPS でリクエストを送ると、HTML が返ってきます。ブラウザは HTML を読んで、必要な CSS・JavaScript・画像も同じように取ってきます。最後に JavaScript が Firestore からランキングのデータを取ってきて、画面に表示します。

**流れ（4段階）**
1. **名前解決**：DNS でドメイン名 → IP アドレスに変換
2. **リクエストとレスポンス**：その IP アドレスのサーバー（Firebase Hosting）に HTML を頼み、返してもらう
3. **追加のファイル**：HTML に書かれた CSS・JS・画像を取ってくる
4. **データの取得と表示**：JS が Firestore からランキングを取ってきて画面を組み立てる

**押さえるキーワード**
- DNS：ドメイン名を IP アドレスに変換する仕組み（電話帳）
- リクエスト（頼む）とレスポンス（返す）
- HTTPS：暗号化された通信

### Q. URL の `?game=warp-room` は何をしているんですか？

**答えの例**
> クエリパラメーターで、どのゲームのランキングを表示するかを渡しています。ランキングのページは `ranking.html` の1つだけで、JavaScript がこの値を読んで表示するゲームを切り替えています。ゲームが21本あってもページを21個作らずに済み、ゲームの追加もデータを足すだけで対応できます。

### Q. 独自ドメインは使わなかったんですか？

**答えの例**
> 使いませんでした。QR コードを印刷する前に URL を確定させる必要があったのですが、独自ドメインは DNS の設定が反映されるまで時間がかかることがあり、間に合わないおそれがありました。来場者は QR コードから開くので覚えやすさも重要ではなく、Firebase が無料で用意してくれる `web.app` のサブドメインで十分だと判断しました。長く使うなら、サービスを乗り換えても URL が変わらない独自ドメインにする価値はあると思います。

## テーマ1：ホスティング

### Q. このサイトは、どうやってインターネットに公開しているんですか？

**答えの例**
> Google の Firebase Hosting に、HTML・CSS・JavaScript・画像などの静的ファイルを置いて公開しています。ファイルは `firebase deploy` というコマンド1つで送れます。見る人のブラウザは、まず Firebase Hosting から HTML などのファイルを受け取り、そのあと JavaScript がデータベースの Firestore からランキングのデータを取ってきて、画面を組み立てています。

**押さえるキーワード**
- Firebase Hosting（「ファイヤーホスティング」ではない）
- 静的ファイル（置いてあるファイルをそのまま返すだけ）
- `firebase deploy` で公開
- 画面の中身は、ブラウザの JavaScript が Firestore から取ってきて組み立てる

### Q. なぜ Firebase Hosting を選んだんですか？

**答えの例**
> 開発期間が1日しかなかったので、公開までの手間が一番少ないものを選びました。Firebase Hosting は HTTPS と CDN が最初から付いていて、サーバーの設定や管理をしなくて済みます。また、スコアの保存に Firestore、管理者のログインに Authentication を使うことにしていたので、同じ Firebase にそろえました。手間が減るだけでなく、ログインした人の情報をそのままデータベースのセキュリティルールで使えるので、「管理者だけが記録を修正できる」という制限を簡単に、確実に書けたのも理由です。

**深掘りされたときのために**
- **他の選択肢との比較**（下の表）を言えると強い
- **弱点も言える**ようにしておく：Firebase 独自の書き方になるので、別のサービスに移るときは書き直しが多い（乗り換えにくい）

| 公開方法 | 公開までの手間 | 今回選ばなかった理由 |
|---|---|---|
| 自分でサーバーを用意（VPS など） | 多い。OS・Webサーバーの設定、HTTPS の証明書、セキュリティの更新、障害対応まで全部自分 | 1日では間に合わない。管理も続けないといけない |
| GitHub Pages | 少ない。リポジトリに置くだけ | 静的ファイル専用。データベースとログインを別のサービスで用意する必要がある |
| Vercel / Netlify | 少ない。GitHub と連携して自動で公開 | 公開は簡単だが、データベースとログインは別のサービスを組み合わせる必要がある |
| AWS（S3＋CloudFront） | 中くらい。保存場所・CDN・証明書をそれぞれ設定 | 設定項目が多く、慣れていないと時間がかかる |
| **Firebase Hosting** | **少ない。コマンド1つ** | 公開・データベース・ログインが1つのサービスでそろう |

### Q. Firebase でそろえると何がいいんですか？手間の問題だけですか？

**答えの例**
> 手間が減るのが一番大きいですが、それだけではありません。Authentication でログインした人の情報（UID）が、Firestore のセキュリティルールの中で `request.auth` としてそのまま使えるので、「管理者の UID の人だけが修正できる」というルールを1行で書けます。別々のサービスを組み合わせると、ログインの情報をデータベース側に渡す仕組みを自分で作る必要があり、そこにミスがあるとセキュリティの穴になります。また、公開・ルール・インデックスを同じコマンドでまとめて反映できるので、設定の反映漏れも起きにくいです。
