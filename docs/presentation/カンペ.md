# 発表カンペ（10分・全12枚）

- 目安：全体で約9分。残り1分は余裕
- 速さ：1分あたり300文字くらい。ゆっくりでいい
- 専門用語を言ったら、一言で意味を添える

---

## 1. 表紙（30秒）
- 情報科学専門学校 情報セキュリティ学科の松橋です
- 文化祭（10/24）で使った「ゲーム紹介とハイスコアランキングのサイト」
- 来場者のスマホと会場のモニターで、実際に使われた
- 順番：何を作ったか → どう作ったか → 工夫 → 難しかったところ

## 2. 画面全体（30秒）
- 展示した **21本**を紹介、そのうち **13本**でハイスコアを競える
- 右はトップページを上から下まで
- スマホとモニターの両方で使用
- 開発は**本番前日の1日** → 「当日確実に動く」を最優先に、範囲を絞った
- 「次で、それぞれの部分を説明します」

## 3. トップページの3つの部分（30秒）
- ① **SCORE ENTRY**：一番上。スコア登録の入り口
- ② **注目エリア**：紹介と TOP3 を10秒ごとに自動切り替え。モニターにはここだけ大きく映した
- ③ **ゲーム一覧**：全21本。「スコア登録」「ランキング」ボタン

## 4. 画面（30秒）
- トップ／ランキング／スコア登録の3画面
- 来場者はほぼスマホ → 押しやすさ・読みやすさを意識
- デザインはアーケード風。見本を何案か作って比べて決めた（ランキングと相性がいい、画像が映える）

## 5. 来場者の使い方（50秒）
- ① QRをスマホで読む、または展示PCのブラウザで開く
  - QRは最初ゲームごと（13枚）の予定 → 大変なので**1枚**にまとめた
- ② SCORE ENTRY → ③ ゲームを選ぶ → ④ 名前とスコアを登録
- 登録すると、モニターも全員のスマホも**再読み込みなしで**すぐ入れ替わる
- 一覧の「スコア登録」からなら③をとばせる
- 同じ名前は**最高スコアだけ**、同点は**先に出した人**が上位

## 6. データの流れ（60秒）
- ① ページを開く：Firebase Hosting から HTML・JS・画像を受け取る
- ② ランキング：Firestore（データベース）に「変わったら教えて」と頼んでおく → 自動で届く
- ③ 登録：ブラウザから**直接**書き込む
  - 自分のサーバーがない → 画面のチェックは回避できる
  - → Google 側の**セキュリティルール**がすべてチェック、OKなら保存 → ②で全員へ
- ④ 管理：Authentication でログイン、UID をルールで確認
- 画面は HTML/CSS/JS（ビルドなし）。期限1日なので慣れた技術で、説明できるコードに

## 7. なぜ Firebase か（50秒）
- 公開だけなら GitHub Pages や Vercel も簡単
- 差が出るのは**データベースとログイン**も必要なとき → 他は別サービスと組み合わせ
- 自分でサーバー → OS・HTTPS・更新まで自分。1日では無理
- Firebase：全部そろう ＋ **ログイン情報がそのままルールで使える**（管理者だけ修正、を確実に書ける）
- 弱点：独自の書き方で**乗り換えにくい**。期限と規模を優先して選んだ

## 8. 工夫1：最高スコアだけ（60秒）
- **名前をそのまま記録の ID** に → 同じ名前は同じ記録へ。1人1件
  - 毎回新しい記録だと、表示のたびに全部読んで集計 → 遅い・無料枠も減る
- 上書きは**前より良いときだけ**。ルールにも書いた → 画面を通さなくても記録は下がらない
- 日時は**サーバーの時刻だけ** → 同点の順位をごまかせない
- 同時に登録されても壊れないよう**トランザクション**（読む・比べる・書くを1つに）

## 9. 工夫2：変更に強く（50秒）
- ゲーム情報は HTML に書かず **games.json** に → 足すだけでページに出る
- 開発中にゲームが増えたとき、文化祭後にランキングを追加したときも、**プログラムは変えずに**対応
- スコアの設定を「並び順」「表示形式」「単位」に分けた → 組み合わせで新パターンに対応
- スコアは全部**整数**（タイムは秒：2:12 → 132）→ 大小だけで並べられる

## 10. 工夫3：二重のチェック（60秒）
- 画面側 ＝ **使いやすさ**（入力ミスをすぐ教える）。回避はできる
  - NGワードは表記をそろえてから照合（「ﾊﾞ カ」も弾く）
- ルール ＝ **安全**（Google 側で動く、回避できない）
  - データの形・サーバーの時刻・管理者の UID だけ修正
- 直接書き込む攻撃を**6種類**試して、**すべて拒否**を確認
- 正直に：NGワードは今は画面側だけ → 今後サーバー側へ

## 11. 結果と今後の展望（2分10秒）

**【先に口頭で】難しかったところ（60秒）**
- **症状**：ゲームを追加して更新 → ある PC だけトップがほぼ空。他の端末は正常 → その PC を調べた
- **原因**：ブラウザの**キャッシュ**。Firebase の初期設定で1時間保存 → 新しい HTML ＋ 古い JS の**食い違い** → エラーで処理が止まった
- **対策**：HTML・JS は毎回新しいか確認（no-cache）、画像だけ保存。**種類ごとに分けた**
- **学び**：本番前に直せた。前に開いたことのある端末でも確認する

**結果**
- 13本中9本で登録、合計 **23件**

**今後の展望**
- 詳しい紹介ページ：games.json に項目を足し、ランキングと同じく1ページを使い回す
- プレイ映像：動画は重い → 動画サービスに置いて埋め込む
- スコアが出ないゲームも盛り上げる：一番盛り上がったのはスコアが出ないゲーム → **難しいモードの挑戦人数・クリア人数**を表示
- 長期：ページからゲームを起動 → ブラウザは安全のため PC のプログラムを直接動かせない → **WebGL** などブラウザで動く形に

## 質疑応答で聞かれそうなこと（ひとことで）

| 質問 | 答えのキーワード |
|---|---|
| サーバーがないのにどう守る？ | セキュリティルール（Google 側）。画面は回避できる。攻撃6種類を確認 |
| 認証で守っている？ | 認証は「誰か」を確かめるだけ。止めているのはルール（UID を確認） |
| API キーが公開されていて大丈夫？ | Firebase のキーは名札。権限はルール次第。AI の API キーはサーバー側だけ |
| API と SDK の違いは？ | API ＝ 頼み方のルール（窓口）、SDK ＝ それを使う道具 |
| なぜ SQL じゃない？ | 並べて上から取るだけ。リアルタイム更新が標準。集計が必要なら SQL |
| 自動更新の仕組みは？ | onSnapshot：「変わったら教えて」と頼んでおく |
| 同時に登録されたら？ | トランザクション＋ルールで「上がるときだけ」 |
| no-cache で遅くならない？ | 保存はする、毎回確認だけ。変わってなければ 304 で短い返事 |
| AI は使った？ | 使った。要件・設計の判断（登録方式・不正対策・デザイン）は比べて自分で決めた。コードは説明できるまで理解した |
| 文化祭のあとは？ | 登録を締め切り（画面とルールの両方）、当日の結果として公開中 |

詳しい答え方は [interview-qa.md](../interview-qa.md) にある。
