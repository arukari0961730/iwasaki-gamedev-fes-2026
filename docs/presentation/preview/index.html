Authentication

画面は HTML / CSS / JavaScript（ビルドなし）。データの守りは Google 側で動くセキュリティルールが担当

なぜ Firebase か

公開の方法公開までの手間データベースとログイン
自分でサーバーを用意多い（OS・HTTPS・更新も自分）自分で用意して管理
GitHub Pages少ない別のサービスと組み合わせる
Vercel / Netlify少ない別のサービスと組み合わせる
Firebase（採用）少ない（コマンド1つ）同じサービスでそろう

ログイン情報がルールで使える

ログインした人の UID がそのまま届くので、「管理者だけ修正できる」を確実に書ける

弱点もわかったうえで

独自の書き方になるので乗り換えにくい。期限と規模を優先して選んだ

工夫 1

「同じ人は最高スコアだけ」をデータの形で実現

名前をそのまま記録のIDに

games / warp-room /
scores / あまちゃ
　score: 345
　achievedAt: 10/24 13:05

同じ名前は同じ記録を見に行くので、1人1件にまとまる。表示のたびの集計も不要

上書きはスコアが上がるときだけ

allow update: if
　新しいスコア > 今のスコア
　&& 日時 == サーバーの時刻

セキュリティルールで制限。読む→比べる→書くはトランザクションで1つの処理に

工夫 2

データと見た目を分けて変更に強く

ゲーム情報は games.json に

"name": "WarpRoom!",
"ranking": {
　"enabled": true,
　"order": "desc",
　"format": "points",
　"unit": "部屋"
}

ゲームの追加はデータを足すだけ

ページはデータを読んで自動で並べる。並び順・表示形式・単位を分けたので、組み合わせを変えるだけ

2:12 → 132

スコアはすべて整数で保存（タイムは秒）。並べ替えが単純で誤差も出ない

工夫 3

画面とルールの二重のチェック

画面側のチェック

役割：使いやすさ（回避はできる）

  • NGワード（表記をそろえてから照合）
  • 名前は12文字まで
  • タイムの秒は59まで

セキュリティルール

役割：安全（Google 側で動く）

  • 項目の過不足・文字数・整数か
  • 日時はサーバーの時刻だけ
  • 修正・非表示は管理者の UID だけ

画面を通さず直接書き込む攻撃を6種類試し、すべて拒否されることを確認

難しかったところ

更新したら、一部のPCだけ画面が空になった

症状

ゲームを追加して公開すると、あるPCだけトップがほぼ空。他の端末は正常

原因

ブラウザが古いJSを1時間キャッシュ。新しいHTMLと食い違いエラーに

対策

HTML・JSは毎回確認（no-cache）、画像は保存。種類ごとに分けた

学び

前に開いたことのある端末でも確認する。本番前に直せた

Firebase Hosting の初期設定：Cache-Control: max-age=3600（1時間は確認せずに使ってよい）
